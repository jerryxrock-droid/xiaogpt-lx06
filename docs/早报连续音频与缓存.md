# 早报连续音频与缓存

更新：2026-10-22。

## 问题与证据

用户反馈等待长、播报断续、小爱提示“回复内含敏感信息”。日志显示最近一次触发12:25:46、归档12:27:18，现场准备约92秒。旧流程先完整采集核验及摘要，再按来源多次调用小米文本转语音，调用间需要等待，部分文本也可能被小米拒绝。模型生成成功不能证明音箱成功播报。

## 本次改动

- 30分钟以内、原文仍在48小时范围内的缓存优先使用，音频按文本哈希复用，不重复联网搜索和改写。
- 没有有效缓存时只创建一个准备任务，重复请求复用它。收到“早报”后立即开始准备，并在本轮等待完成，准备好后自动开始播放，无需再说一次“早报”。等待期间说其他指令会中断本次等待，但准备任务仍在后台继续；稍后再说“早报”可直接使用已完成的缓存。准备失败会明确提示。不定时调用API，不主动定时播报。
- 使用 Microsoft Edge 神经语音“晓晓”（`zh-CN-XiaoxiaoNeural`，语速 +8%）合成整份早报，转换成一段 MP3，通过现有小米音频 URL 播放接口交给 LX06。Edge 不可用（断网、接口失败、返回空音频或超时）时，自动回退到 macOS 本地 `say`（美佳 Meijia，语速 195），不中断早报流程。新闻不再走小米逐段文本转语音；这不是修改新闻词语，也不保证小米所有播放请求都不会被拒绝。
- 音箱声音会与原来的小爱文字播报声有所不同。普通AI问答和其他操作提示仍用原有mi TTS。
- 音频开头注明资料截至时间，避免把缓存当成刚刚发生的信息。
- Mac仅在私有局域网接口监听临时端口，只通过随机令牌URL提供指定早报MP3；不提供目录浏览、配置、笔记或其他任意文件。令牌有期限并在播放结束/取消后移除。
- 音箱需能通过局域网访问Mac。Mac睡眠、换网或防火墙阻止取音频时会明确失败，不把接口接收当作播放成功。
- 保留新指令打断：取消当前播放任务后由原有停止音箱接口中断；准备中的只读检索任务不被重复语音请求反复重启。服务退出时清理后台任务和HTTP服务。

## 验证范围

116项自动化回归通过，新增缓存过期/未来日期拒绝、准备任务合并、随机URL访问范围、Range请求和播放失败不报成功。实机短音频测试确认：播放接口接受、音箱实际GET音频、音箱状态为正在播放。

上一轮12条新闻生成的完整音频约89.4秒，首次本地合成与转码约2.24秒；后续复用已有MP3。音箱完整早报的实际听感及是否仍有拦截提示，等待用户语音验收，不把短音频链路测试当作已完全解决。

## 文件

- `briefing_audio.py`：缓存、合成、临时音频服务和整段播放。
- `runtime.py`：早报入口接入连续音频播放器。
- `state/advanced/briefing_latest.json`：已核验新闻与生成时间。
- `state/advanced/briefing-audio/`：仅新闻音频缓存，不含日历或笔记内容。

不调整小爱固件、不连接蓝牙、不重新编译控制中心、不新增屏幕录制授权。
